## 2. 部署缺口与修复

旧 `apps/loom-platform/license_server/deploy.sh` 存在四个部署级缺口：

1. 只部署 `server.py`，没有部署其依赖的完整 `luming_license/` 模块树；
2. 配置发布中转令牌时会重写整个环境文件，可能擦除 entitlement 服务令牌和其他设置；
3. 健康检查只证明进程存活，没有证明 entitlement 路由已经加载；
4. 程序切换前后的失败路径没有统一覆盖环境和程序回滚。

提交 `3ce44e6` 已完成以下加固：

- 新增 `luming_license/deploy_env.py`，以原子写入方式只更新指定环境变量并保留其他配置；
- 部署完整 `server.py + luming_license/`，上传内容先编译，再在同一文件系统内暂存和切换；
- 部署前备份程序、环境和 SQLite；失败时回滚程序与环境；
- entitlement 服务令牌成为强制前置条件；无凭据路由探针必须返回 `401`，`404` 或 `503` 均判为部署失败；
- SQLite 只备份和执行 `quick_check`，失败时绝不自动降级数据库，避免用旧库覆盖部署期间的有效写入；
- Relay 状态上下文只比较稳定授权字段，且错误响应同时保留结构化对象和兼容字段。

提交 `991ad39` 又为已识别的桥接拓扑增加 `apps/loom-platform/server/deploy.sh`：

- 缺少任一 entitlement 配置时在 `systemctl stop` 前拒绝继续；
- 不 `source`、生成、复制或改写 `bridge.env` 和签名私钥；
- 候选先编译，并用生产环境配置加载候选、校验固定 key ID 与公钥信任锚；
- 备份旧程序和环境文件，使用同文件系统暂存与原子切换；
- 启动后同时验证 `/health` 与 `/api/openclaw/entitlements/public-key` 的 JSON 合同；
- 强制验证部署前后环境文件 SHA256 不变，失败时恢复旧程序并重新启动旧服务。

## 5. 生产执行顺序与验收门

生产变更必须在用户再次明确确认后执行，且顺序固定：

1. 重新核对已只读发现的两个真实 unit、工作目录、环境文件、反向代理路由和 SQLite 路径；
2. 生成脱敏清单并确认备份空间；
3. 通过安全通道生成一个专用服务间 Token，在授权服务和桥接环境中配置同一值；配置持久化 bind DB、独立 bind-ticket Secret 和与客户端信任锚匹配的既有签名私钥来源；不在命令行、日志或候选包中出现值；
4. 先部署授权服务，要求健康、SQLite、进程和 entitlement `401` 路由探针全部通过；
5. 再用守护脚本部署桥接服务，要求本地和公网公共密钥路由 `200` 且返回可解析公钥；
6. 使用现有模型账号会话执行不含授权码的 current/refresh 验证；
7. 只从用户表格后 50 个候选中使用先前安全选定的 1 个授权码；明文只驻留进程内；
8. 验证账号绑定、Desktop 刷新、矩阵解锁和同码重复请求幂等；
9. 记录状态码、时间、匿名身份摘要和授权版本，不记录授权码、Token、私钥或账号明文。

任一步失败都停止后续动作。程序或环境失败可按备份回滚；数据库不得自动回滚。正式发布、更新清单、支付、评论、私信和其他对外动作均不在本门禁的默认授权范围内。
